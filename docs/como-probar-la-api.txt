Lee primero esto, te ahorra la confusión más común:

  ⚠️ EL LOGIN CON GOOGLE **NO** SE PRUEBA DESDE SWAGGER.

  Google necesita abrir SU pantalla, que tú elijas tu cuenta y que te regrese
  a la aplicación. Eso solo pasa en la barra de direcciones del navegador.
  Si le picas "Execute" al endpoint de Google dentro de Swagger, no va a
  funcionar y no es que esté roto.

  Swagger sirve para TODO LO DEMÁS: ahí pegas el token que te dio Google (o el
  login normal) y pruebas los endpoints protegidos.


================================================================================
0. ANTES DE EMPEZAR: LEVANTAR EL PROYECTO
================================================================================

Abre Docker Desktop y luego, desde la raíz del repositorio:

    docker compose up -d

Después una terminal por servicio (5 terminales):

    cd apps/backend/api-gateway            && pnpm start:dev
    cd apps/backend/auth-service           && pnpm start:dev
    cd apps/backend/venues-events-service  && pnpm start:dev
    cd apps/backend/purchases-service      && pnpm start:dev
    cd apps/backend/tickets-service        && pnpm start:dev

Comprueba que los 5 respondan:

    for p in 3001 3002 3003 3004 3005; do curl -s http://localhost:$p/health; echo ""; done

Si alguno falla, casi siempre es una de estas tres:
  - Docker Desktop cerrado
  - Falta el archivo .env (cópialo del .env.example de ese servicio)
  - Falta correr "pnpm install" después del último pull

1. DÓNDE ESTÁ SWAGGER
================================================================================

Hay dos interfaces, las dos sirven. Usa la que te acomode:

  Swagger UI (la clásica, con el botón "Authorize"):
      http://localhost:3001/swagger/venues     <- la tuya
      http://localhost:3001/swagger/auth
      http://localhost:3001/swagger/purchases
      http://localhost:3001/swagger/tickets

  Scalar (más bonita):
      http://localhost:3001/docs/venues
      http://localhost:3001/docs/auth
      http://localhost:3001/docs/purchases
      http://localhost:3001/docs/tickets

Para tu bloque (eventos, zonas, secciones, asientos) usa **/swagger/venues**.

2. PROBAR SIN GOOGLE: LOGIN NORMAL (LO MÁS RÁPIDO)
================================================================================

No necesitas Google para nada de tu trabajo. Con correo y contraseña basta.

PASO 1 — Consigue un token

  Abre:  http://localhost:3001/swagger/auth
  Busca: POST /auth/login
  Click en "Try it out", pega esto en el cuerpo y dale "Execute":

      {
        "email": "angel@test.com",
        "password": "Test1234"
      }

  En la respuesta te va a salir algo así:

      {
        "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9....",
        "user": { "name": "...", "role": { "name": "ORGANIZER" } }
      }

  COPIA el valor de "token" completo, SIN las comillas.

PASO 2 — Pégalo en Swagger

  Ve a  http://localhost:3001/swagger/venues
  Arriba a la derecha hay un botón que dice **Authorize** (con un candadito).
  Click ahí, pega el token en el campo, dale "Authorize" y luego "Close".

  Ojo: solo pega el token pelón. NO escribas la palabra "Bearer" adelante,
  Swagger la agrega sola.

PASO 3 — Ya puedes probar

  Los endpoints con candado cerrado ahora funcionan. Prueba
  POST /events y debería responder 201 en vez de 401.

  El token dura 1 día. Si de pronto todo te empieza a dar 401, vuelve al
  paso 1 y saca uno nuevo.

USUARIOS QUE YA EXISTEN EN LA BASE

  angel@test.com     / Test1234      rol ORGANIZER   <- usa este para tu bloque
  admin@test.com     / Admin1234     rol ADMIN
  cliente1@test.com  / Cliente1234   rol CLIENT

  Si quieres uno tuyo: POST /auth/register con nombre, email y password
  (mínimo 8 caracteres). Sale con rol CLIENT.

3. PROBAR EL LOGIN CON GOOGLE (EN EL NAVEGADOR)
================================================================================

REQUISITO: Angel tiene que haber agregado tu correo de Google como "usuario de
prueba" en la consola de Google Cloud. Si no lo hizo, te va a salir
"Acceso bloqueado" aunque todo lo demás esté bien. Pídeselo primero.

PASO 1 — Pega esta dirección en la barra del navegador (NO en Swagger):

    http://localhost:3002/auth/google

PASO 2 — Google te muestra su pantalla. Elige tu cuenta y acepta.

PASO 3 — Te regresa a una página con un JSON parecido a este:

    {
      "token": "eyJhbGciOi....",
      "user": {
        "name": "Tu Nombre",
        "email": "tucorreo@gmail.com",
        "provider": "GOOGLE",
        "role": { "name": "CLIENT" }
      }
    }

  Ese "token" sirve igual que el del login normal: cópialo y pégalo en el
  botón "Authorize" de Swagger (paso 2 de la sección anterior).

QUÉ ES NORMAL Y NO ES UN ERROR

  - Que te salga JSON pelón en el navegador. Todavía no hay pantalla bonita;
    eso se hace cuando conectemos el frontend.
  - Que si RECARGAS esa página te diga "state is invalid or expired". Es a
    propósito: cada intento de login sirve una sola vez, por seguridad.
    Para probar otra vez, entra de nuevo a /auth/google desde cero.
  - Que tu usuario salga con rol CLIENT. Todos entran así.

SI QUIERES QUE TU CUENTA DE GOOGLE SEA ORGANIZADORA

  Pídele a Angel que te la ascienda. Él lo hace con el usuario admin:
  PATCH /users/{id}/role  con  { "roleId": "22222222-2222-4222-8222-222222222222" }


================================================================================
4. CÓMO SABER QUÉ NECESITA CADA ENDPOINT
================================================================================

En Swagger, los endpoints con un CANDADITO piden token. Los que no lo tienen
son públicos (todo el catálogo: ver eventos, recintos y categorías).

El mapa completo de quién puede hacer qué está en:  docs/doc.md

Resumen para tu bloque (eventos, zonas, secciones, asientos):

  LEER    (GET)                    público, sin token
  CREAR / EDITAR / BORRAR          token con rol ORGANIZER o ADMIN

Por eso el usuario angel@test.com (ORGANIZER) es el que te sirve.


================================================================================
5. LOS DOS ERRORES QUE TE VAN A SALIR Y QUÉ SIGNIFICAN
================================================================================

  401 Unauthorized
      No mandaste token, ya venció, o lo pegaste mal.
      → Saca uno nuevo con POST /auth/login y vuelve a darle Authorize.

  403 Forbidden
      El token está bien pero tu rol no alcanza.
      → Te pasa si usas cliente1@test.com para crear un evento.
        Usa angel@test.com, que es ORGANIZER.

  400 Bad Request
      Los datos del cuerpo no pasaron las validaciones. Lee el campo
      "message" de la respuesta: te dice exactamente qué campo está mal.

  409 Conflict
      La regla de negocio no lo permite (por ejemplo, borrar una sección que
      ya está asignada a una zona de evento). Es el tipo de error que TÚ vas
      a agregar en tu bloque.


================================================================================
6. SI PREFIERES LA TERMINAL EN VEZ DE SWAGGER
================================================================================

Sacar el token y guardarlo en una variable:

    TOKEN=$(curl -s -X POST http://localhost:3001/auth/login \
      -H "Content-Type: application/json" \
      -d '{"email":"angel@test.com","password":"Test1234"}' \
      | python3 -c "import json,sys; print(json.load(sys.stdin)['token'])")

Usarlo:

    curl -s http://localhost:3001/auth/me -H "Authorization: Bearer $TOKEN"

    curl -s "http://localhost:3001/events?page=1&limit=5"

    curl -s -X PATCH http://localhost:3001/events/<ID_EVENTO>/status \
      -H "Content-Type: application/json" \
      -H "Authorization: Bearer $TOKEN" \
      -d '{"status":"PUBLISHED"}'

Ese último es justo el que vas a modificar en tu tarea 1: hoy responde 200
aunque el evento no tenga zonas ni precios, y debe responder 409.

7. SI ALGO NO JALA
================================================================================

  "No me aparece el botón Authorize"
      Estás en Scalar (/docs/...) en vez de Swagger UI (/swagger/...).
      Scalar también deja mandar el token, pero el botón se ve distinto.

  "Todo me da 401 aunque acabo de pegar el token"
      El JWT_SECRET tiene que ser EXACTAMENTE EL MISMO en los .env de los
      cuatro servicios. Si en venues-events lo tienes distinto, auth te da
      el token pero venues-events lo rechaza. Revisa los cuatro archivos.

  "El servicio no arranca y habla de una migración"
      Corre en ese servicio:  pnpm exec prisma migrate dev

  "Google me dice Acceso bloqueado"
      Tu correo no está en la lista de usuarios de prueba. Pídeselo a Angel.

  Cualquier otra cosa, mándale a Angel el error COMPLETO de la terminal, no
  solo la última línea.
