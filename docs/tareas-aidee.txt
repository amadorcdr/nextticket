TAREA 1 — Modelo de usuarios y roles  [EMPIEZA POR AQUÍ]
--------------------------------------------------------------------------------
Archivo: apps/backend/auth-service/prisma/schema.prisma

QUÉ HAY HOY (el modelo completo, no falta nada del recorte):

    model User {
      id        String   @id @default(uuid())
      name      String
      createdAt DateTime @default(now())
      updatedAt DateTime @updatedAt
    }

Sin email, sin contraseña, sin rol. Así no se puede autenticar a nadie.

NO INVENTES EL MODELO: ya está diseñado en la raíz del repo, en nextticket.sql,
líneas 75 a 139. Ahí están las tablas roles, permissions, role_permissions y
users. La tabla users del diseño es:

    id, created_at, created_by, last_modified_by, status (boolean),
    updated_at, name, email (UNIQUE), password, role_id (FK a roles)

QUÉ HACER:
  - Traducir a Prisma los modelos User y Role como están en ese SQL, respetando
    el índice único de email y la relación con roles.
  - Agregar los campos que OAuth necesita y que el diseño original no tiene
    (porque se pensó solo para login con contraseña):
        provider        (LOCAL / GOOGLE / etc.)
        providerId      (el id del usuario en el proveedor)
    Y hacer password OPCIONAL, porque un usuario de OAuth no tiene contraseña.
  - Crear la migración y COMMITEARLA completa, con su migration.sql:
        pnpm exec prisma migrate dev --name add_users_roles_auth
  - Sembrar los roles. Según el README (sección 11) son: Cliente, Organizador
    y Validador. Confirma con el equipo si quieren además un Administrador.

DECISIÓN QUE DEBES CONSULTAR CON EL EQUIPO:
El diseño original trae permissions y role_permissions (permisos finos por
recurso). Para lo que necesitamos ahora basta con el rol. Propón hacer solo
roles ahora y dejar los permisos para después, y déjalo escrito en el PR.

CUIDADO: crear esta migración obliga a todos a correr "pnpm exec prisma
migrate dev" en auth-service. Avisa en el grupo cuando la mergees.

TAREA 2 — Registro, login y OAuth en auth-service
--------------------------------------------------------------------------------
Crea el módulo: apps/backend/auth-service/src/auth/
    auth.controller.ts, auth.service.ts, auth.module.ts, dto/

ENDPOINTS MÍNIMOS:
    POST /auth/register     nombre, email, contraseña -> crea usuario rol Cliente
    POST /auth/login        email + contraseña -> devuelve JWT
    GET  /auth/google       inicia el flujo OAuth
    GET  /auth/google/callback   crea o encuentra al usuario y devuelve JWT
    GET  /auth/me           datos del usuario del token

REGLAS QUE NO SE NEGOCIAN:
  - Las contraseñas se guardan con bcrypt (o argon2). NUNCA en texto plano.
  - El campo password JAMÁS se devuelve en una respuesta. Revisa también
    GET /users y GET /users/:id, que hoy devuelven el usuario completo.
  - El JWT lleva como mínimo: sub (id del usuario), email y role.
  - El secreto del JWT y las credenciales de Google se leen de variables de
    entorno con ConfigService, nunca escritas en el código.

VARIABLES DE ENTORNO:
  Agrega a apps/backend/auth-service/.env.example (con valores de ejemplo, NO
  los reales):
        JWT_SECRET=cambiame
        JWT_EXPIRES_IN=1d
        GOOGLE_CLIENT_ID=tu-client-id
        GOOGLE_CLIENT_SECRET=tu-client-secret
        GOOGLE_CALLBACK_URL=http://localhost:3002/auth/google/callback

  ⚠️ NUNCA commitees el .env con las credenciales reales de Google. Si se te
  va una por error, no basta con borrarla en otro commit: hay que revocarla
  en la consola de Google y generar otra.

4. CÓMO PROBAR A MANO
================================================================================

Levantar (Docker Desktop tiene que estar abierto):

    cd apps/backend/purchases-service && docker compose up -d
    cd apps/backend/auth-service && pnpm start:dev

Docs interactivas:
    http://localhost:3002/docs/auth
    o por el gateway: http://localhost:3001/docs/auth

Registro y login:

    curl -s -X POST http://localhost:3002/auth/register \
      -H "Content-Type: application/json" \
      -d '{"name":"Aidee","email":"aidee@test.com","password":"Test1234"}'

    curl -s -X POST http://localhost:3002/auth/login \
      -H "Content-Type: application/json" \
      -d '{"email":"aidee@test.com","password":"Test1234"}'

Usar el token contra otro servicio (aquí se ve si el guard y el gateway
funcionan de verdad):

    curl -s http://localhost:3001/events \
      -H "Authorization: Bearer <TOKEN>"

Pruebas que DEBEN fallar:
    - Sin header Authorization en un endpoint protegido -> 401
    - Con token de Cliente creando un evento -> 403
    - Token manipulado o vencido -> 401

Antes de subir, revisa que compile:
    pnpm exec tsc --noEmit -p tsconfig.json

6. DUDAS FRECUENTES
================================================================================

¿Google OAuth necesita que el proyecto esté en internet?
    No para desarrollo. En la consola de Google Cloud registras
    http://localhost:3002/auth/google/callback como URI de redirección
    autorizada y funciona en local.

¿Dónde guardo el token en el frontend?
    Eso lo define quien haga el front, no lo decidas sola. Tú solo devuélvelo
    en la respuesta del login y documenta su duración.

¿Y si necesito un campo que no está en nextticket.sql?
    Agrégalo, pero dilo en el PR. El SQL es el diseño original y OAuth no
    estaba contemplado ahí, así que es normal que se extienda.

¿Cómo pruebo endpoints protegidos desde las docs?
    Agrega @ApiBearerAuth() al controller y registra el esquema bearer con
    .addBearerAuth() en el DocumentBuilder de main.ts. Así aparece el botón
    para pegar el token.
